# 部署手册

适用于 QuoteFlow 询盘报价平台的测试 / 演示环境（staging）与生产环境。两者用同一套镜像，区别只在环境变量和前面是否有负责 TLS 的反向代理。

## 1. 组成

| 服务 | 镜像 | 说明 |
|---|---|---|
| `web` | `docker/web.Dockerfile`（nginx） | 前端静态文件；`/api` 反代到 `api`；上传上限 60 MB |
| `api` | `docker/api.Dockerfile` 的 `runtime` 阶段（Node 24） | 启动时先 `prisma migrate deploy` 再启动；定时任务（发邮件、截止、催报、清理）在进程内运行，**只能起一个实例** |
| `postgres` | `postgres:15` | 数据库，命名卷 `pgdata` |
| `mailpit` | `axllent/mailpit` | 仅 staging：收下所有邮件供查看，不真正外发 |
| `api-tools` | `api.Dockerfile` 的 `build` 阶段 | 一次性工具：基础数据、演示数据（`profiles: tools`，平时不运行） |

上传文件存在 api 容器的 `/app/storage`（命名卷 `uploads`）。

## 2. 环境要求

- Docker Engine 24+ 与 Docker Compose v2（Windows / macOS 用 Docker Desktop）。
- 首次构建需要能访问 npm 仓库和 Prisma 引擎下载地址（`binaries.prisma.sh`）；网速慢时构建约 10–20 分钟，之后有缓存。
- 内存 2 GB 以上，磁盘按上传文件量预留（规格书单个最大 50 MB）。

## 3. 配置项

staging 的配置在 `docker/staging.env`（从 `docker/staging.env.example` 复制，**不提交到仓库**），compose 文件把它们转成 api 的环境变量。完整的环境变量说明见 [01-技术架构](../01-技术架构.md) §17 与 `apps/api/.env.example`。

| 变量 | 必填 | 说明 |
|---|---|---|
| `POSTGRES_PASSWORD` | 是 | 数据库密码（staging 的 postgres 容器用它初始化） |
| `EXCEL_SIGNING_SECRET` | 是 | 锁定报价 Excel 的签名密钥（≥ 8 位）。**换了以后，之前下载的报价 Excel 都不能再导入**，上线后不要随意更换 |
| `EXCEL_SHEET_PASSWORD` | 是 | 锁定报价 Excel 的工作表保护密码 |
| `APP_BASE_URL` | 否 | 邮件里链接的前缀，默认 `http://127.0.0.1:18080`；对外开放后改成对外地址 |
| `SMTP_HOST` / `SMTP_PORT` / `SMTP_SECURE` / `SMTP_USER` / `SMTP_PASS` / `MAIL_FROM` | 否 | 默认发到自带的 Mailpit；接真实邮件服务时修改 |
| `COOKIE_SECURE` | 否 | 只有 HTTPS 访问时才能设为 `true`（否则浏览器不回传会话 cookie，无法登录） |

compose 里固定的几项：`NODE_ENV=production`、`API_HOST=0.0.0.0`（只在容器网络里监听）、`TRUST_PROXY=uniquelocal`（信任同一网络里 nginx 转发的客户端 IP，登录限流与审计日志按真实 IP 记录）、`STORAGE_DIR=/app/storage`、`JOBS_ENABLED=true`。生产环境 `NODE_ENV=production` 时如果 `EXCEL_SIGNING_SECRET` 还是开发默认值，api 拒绝启动。

## 4. 首次部署（本机 staging）

在仓库根目录执行（Windows 用 PowerShell 或 Git Bash 都可以）：

```bash
cp docker/staging.env.example docker/staging.env      # 然后编辑，改掉三个 change-me
docker compose -f docker/compose.staging.yml --env-file docker/staging.env up -d --build
docker compose -f docker/compose.staging.yml --env-file docker/staging.env ps     # api、web 显示 healthy
```

网络慢时（开发机下载 npm 包约 270 KB/s），首次构建要在镜像里下载几百 MB 的依赖，可能一小时以上，甚至因下载超时（`ETIMEDOUT`）失败。本机执行过 `npm install` 的话，先把本机 npm 缓存里的包交给镜像构建，镜像里就只需下载 Linux 专用的少量原生包：

```bash
node scripts/docker-npm-seed.mjs        # 复制约 180 MB 到 docker/.npm-seed（不提交）
```

构建失败时直接重新执行即可，已经下载的包保存在构建缓存里。也可以分步构建再启动：

```bash
C="docker compose -f docker/compose.staging.yml --env-file docker/staging.env"
$C --profile tools build api-tools && $C build api && $C build web && $C up -d
```

初始化数据（只在空库上执行一次）：

```bash
# 基础数据：角色、字典、内部账号、PPL 模板、材料分类与材料、供应商与门户账号（演示账号密码都是 Passw0rd!）
docker compose -f docker/compose.staging.yml --env-file docker/staging.env --profile tools run --rm api-tools npx prisma db seed
# 演示数据（可选）：D1–D8 与 60 张历史询价，约 1 分钟
docker compose -f docker/compose.staging.yml --env-file docker/staging.env --profile tools run --rm api-tools node dist-seed/prisma/seed-demo.js
```

访问：

- 系统：`http://127.0.0.1:18080`（`admin` / `Passw0rd!`；供应商用联系邮箱登录，见 [验收清单](验收清单.md)）
- 邮件：`http://127.0.0.1:18026`（Mailpit）

端口只绑定 `127.0.0.1`，局域网和外网都访问不到。给客户演示需要另外配置对外访问入口（反向代理或内网穿透），并把 `APP_BASE_URL` 改成对外地址。

**上线前必须改掉演示账号的密码**（系统设置 › 用户 › 重置密码），或者不执行基础数据里的演示账号部分、由管理员新建账号。

## 5. 升级

```bash
git pull
docker compose -f docker/compose.staging.yml --env-file docker/staging.env up -d --build
```

api 启动时自动执行 `prisma migrate deploy`，把数据库迁移到新版本（迁移只增不删，失败时 api 不会启动，日志里有原因）。升级前先做一次备份（§6）。

查看日志：`docker compose -f docker/compose.staging.yml --env-file docker/staging.env logs -f api`

## 6. 备份与恢复

备份（数据库 + 上传文件）：

```bash
scripts/backup.sh                       # 默认备份 quoteflow-staging，输出到 ./backups/quoteflow-staging-<时间>/
scripts/backup.sh quoteflow-prod /data/backups
```

输出目录里有 `quoteflow.dump`（`pg_dump -Fc`）和 `storage/`（上传文件）。生产环境每天定时执行一次，备份目录再复制到另一台机器或对象存储。

恢复（会覆盖现有数据，先停 api 和 web）：

```bash
P=quoteflow-staging; B=./backups/quoteflow-staging-20261101-120000
docker compose -f docker/compose.staging.yml --env-file docker/staging.env stop api web
docker exec -i $P-postgres-1 pg_restore -U quoteflow -d quoteflow --clean --if-exists < $B/quoteflow.dump
docker cp $B/storage/. $P-api-1:/app/storage
docker compose -f docker/compose.staging.yml --env-file docker/staging.env start api web
# docker cp 拷进去的文件属主是 root，api 以 node 用户运行：容器启动后改回属主
docker exec -u root $P-api-1 chown -R node:node /app/storage
```

Git Bash 下执行 `docker cp` / `docker exec` 时如果容器内路径被改写成 Windows 路径，在命令前加 `MSYS_NO_PATHCONV=1`。2026-11-01 在本机 staging 上按本节完整做过一次备份与恢复（数据库与上传文件都恢复，文件可正常下载）。

## 7. 停止与清理

```bash
docker compose -f docker/compose.staging.yml --env-file docker/staging.env stop      # 停止，保留数据
docker compose -f docker/compose.staging.yml --env-file docker/staging.env down      # 删除容器，保留数据卷
docker compose -f docker/compose.staging.yml --env-file docker/staging.env down -v   # 连数据一起删除（不可恢复）
```

只操作 `quoteflow-` 开头的容器、卷和镜像；不要对整台机器执行 `docker system prune` 之类的清理。

## 8. 生产部署（部署地点确定后执行）

部署地点未定（待确认事项 A-20）。确定后按下面的清单执行：

1. **服务器**：Linux 云主机 2 核 4 GB 起，安装 Docker；数据盘单独挂载，放数据库卷和上传卷。
2. **配置**：复制 `docker/compose.staging.yml` 为生产用的 compose 文件，去掉 `mailpit`，`SMTP_*` 改成真实邮件服务，`APP_BASE_URL` 改成正式域名，`COOKIE_SECURE=true`，所有密码与密钥重新生成。
3. **TLS**：web 的端口只发布到本机，前面放负责 HTTPS 的反向代理（Caddy 或 Nginx + 证书），把 HTTP 重定向到 HTTPS。如果反向代理不在同一个 Docker 网络里，按实际情况调整 `TRUST_PROXY`（填反向代理的 IP 或网段），否则登录限流会把所有用户当成同一个 IP。
4. **邮件**：用公司域名发信，配置 SPF、DKIM（必要时 DMARC），先给几个内部邮箱发测试邮件确认不进垃圾箱；在"系统设置 › 邮件记录"可以查看发送结果和重发。
5. **备份**：每天定时执行 `scripts/backup.sh`，保留 30 天，异地保存；每季度做一次恢复演练。
6. **备案**：国内云 + 自有域名需要 ICP 备案（1–3 周），确定部署地点后第一时间提交。
7. **上线前**：修改或删除演示账号；不要执行演示数据；在"系统设置 › 系统参数"填写公司名称、地址、电话（邮件抬头与合同打印版使用），确认密封授权角色和积分规则；替换为客户的正式 PPL 模板（[管理员手册](管理员手册.md) §5）。

## 9. 自动化测试

| 命令 | 内容 | 依赖 |
|---|---|---|
| `npm run verify` | lint、类型检查、文案检查、单元测试、api e2e（含权限矩阵、安全复查、密封与隔离测试集） | 本机 Docker 的开发依赖（测试库 `quoteflow_test`） |
| `npm run test:browser` | Playwright 浏览器主流程：建单 → 审批 → 发布 → 三家供应商在线 / Excel / 拒绝 → 提前截止 → 开标 → 比价入围 → 议价成交 → 定标 → 合同审核批准；中英文关键页面截图 | 同上，另需本机安装 Google Chrome；自己在 3100 / 5174 端口起服务、清空并 seed 测试库；不能与 `npm run test:e2e` 同时跑 |
| `node scripts/perf/perf-check.mjs` | 性能抽查（说明见脚本头部） | API 连测试库 |

对 staging 跑浏览器主流程：先把 staging 恢复成只有基础数据的状态（`down -v` 后重新 `up` 并执行基础数据），再在 `apps/web` 下执行 `npx playwright test`，环境变量 `QF_BASE_URL=http://127.0.0.1:18080`（设置后 Playwright 不再自己起服务）。
